# github-writing — 読み手が一読で行動できる文章を書く

GitHub 向けの文章 (PR 本文 / Issue・PR スレッドのコメント / レビューコメント) が対象。
「言いたいことは全部書いてあるが、何をすればいいか分からない」文章を防ぐ。網羅性より
可読性と行動可能性を優先する。ドキュメント全般の絵文字禁止は CLAUDE.md の
Documentation Style 節を継続して守る。

## 4つの役割を混ぜない

事実・判断・依頼・次アクションを段落または見出しで分離する。1つの長い段落に事実と
理由と経緯を詰め込まない。

1. **事実**: 観測・計測・コードから確認できたこと
2. **判断と理由**: 何をどう決めたか、なぜか
3. **依頼**: 相手にしてほしいこと (確認・承認・修正など)。埋もれさせず、探さなくても
   見つかる位置に置く
4. **次アクション**: これを読んだ人が次に何をすればいいか

依頼が無い文章 (質問への回答など) では 3 を省いてよい。ただし省いたことを意識的に
判断すること。

## 用語と網羅性

- 専門用語・内部の task_id・内部でしか通じない略語は、初出で開くか、開けないなら削る。
  相手が知らない語で説明しない
- 「やったこと全部」を書かない。相手の判断や行動に必要な情報だけを本文に置き、根拠・
  ログ・検討経緯は `<details>` に畳むか報告ファイルへのポインタにする
- 冒頭で結論を書く。経緯から書き始めない。読み手は最初の数行で「何の話で、自分は何を
  すればいいか」を掴めること
- 1文だけの段落を空行で細かく区切って縦に間延びさせない。関連する項目は箇条書きに
  まとめ、連続する空行 (2行以上) は作らない

## 投稿前の自己チェック

一読しただけで次の3つをそれぞれ1文で言えるか確認する。言えないなら投稿しない。

- (a) 今どうなっているのか
- (b) 我々が何をどう決めたのか、なぜか
- (c) 自分 (読み手) が何をすればいいのか

たどり着けない。

**1点目 (shelf_detached のブリッジ側実装予定について)**

shelf_detached の検知は PR #48 (head 6d00e13) 時点で未実装です。バグではなく、phase 2 に

## 対象ごとの違い

- **PR 本文**: 読み手はレビュアー。冒頭で「何をレビューしてほしいか」と影響範囲を示す。
  実装過程のログや試行錯誤は `<details>` に畳む
- **Issue・PR スレッドコメント**: 会話の一部であることを意識する。直前の質問に対する
  回答という体裁を保ち、前提の再掲は最小限にする
- **レビューコメント**: 指摘ごとに blocking (このままではマージ不可) か non-blocking
  (nit・提案) かを明示する。これが無いと著者はどこまで直せばよいか判断できない。
  指摘は対象コードを引用してから書き、「どこの話か」を著者に探させない。引用は
  GitHub の行コメントか、本文中のコードブロック引用 + `file:line` の明示のいずれかで
  行う。対象コードを示さない「〜が問題です」「〜を修正してください」だけの指摘は
  書かない
